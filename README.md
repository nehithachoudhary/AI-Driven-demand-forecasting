# AI-Driven Demand Forecasting and Smart Inventory Optimization

A local Flask application for forecasting daily demand at the `Store ID + Product ID + Date` grain and translating forecasts into transparent inventory decisions.

## Dataset

The application uses the existing `data/raw/sales_data.csv` without modifying it. It contains 76,000 observations, 5 stores, 20 products, 5 categories, 4 regions, and daily dates from 2022-01-01 through 2024-01-30. `Demand` is the primary target. The source file is treated as dataset input, not as a claim about real company operations.

## Architecture

`raw CSV -> validation -> processed CSV -> leakage-safe features -> chronological holdout -> Random Forest / XGBoost / SARIMA / LSTM -> metrics and forecasts -> inventory policy -> Flask API -> dashboard`

The wholesale application domain uses SQLite at `instance/wholesale.db`; the raw CSV remains read-only training data. Authentication uses hashed passwords and Flask sessions. Products, sales, inventory transactions, forecasts, alerts, and settings are scoped by the authenticated `user_id`, so customer records are isolated.

## Account Recovery

Registration includes a predefined security question and answer in addition to the existing email, mobile number, and password fields. Security answers are normalized and stored only as Werkzeug password hashes; they are never returned by APIs. Login includes a Forgot Password link that verifies the registered email and mobile number, then verifies the selected account's security answer on the server.

After successful verification, the application stores a short-lived, single-use recovery authorization in SQLite. The reset endpoint validates that authorization server-side, enforces the existing password rules, hashes the new password, invalidates the authorization, and clears the session. The application does not use email, SMTP, OTP, SMS, or external authentication services.

Existing users created before recovery fields were added remain valid for normal login and are not assigned fabricated recovery answers. Their recovery fields remain empty until a supported account-update flow supplies them, so Forgot Password cannot be used for those accounts until recovery information exists. Recovery attempts are rate-limited by purpose and client address with a temporary block after repeated failures.

Lag and rolling features are grouped by store and product. Rolling values are shifted first, so each row only sees prior observations. The latest 60 days are reserved as the chronological test period. Tree models are global across valid store-product rows. SARIMA and LSTM are genuine univariate models evaluated on the documented `S001/P0001` reference series; this keeps their native time-series assumptions intact rather than combining unrelated series. The LSTM scaler is fitted only on the training prefix, and its validation suffix and test period remain chronological with training shuffle disabled.

## Inventory formulas

- `Safety Stock = Z(service level) * historical demand standard deviation * sqrt(lead time)`
- `Reorder Point = average forecast demand per day * lead time + safety stock`
- `Target Stock = forecast demand for the selected horizon + safety stock`
- `Suggested Reorder Quantity = max(0, target stock - latest known inventory)`

Supplier lead time and service level are operational parameters because the dataset does not provide supplier lead times. The dashboard API defaults to 7 days and 95%, and accepts overrides.

## Setup and run

### 1. Clone the repository

Open PowerShell and run:

```powershell
git clone https://github.com/nehithachoudhary/AI-Driven-demand-forecasting.git
cd AI-Driven-demand-forecasting
```

### 2. Create and activate a virtual environment

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
```

If PowerShell blocks activation, run this once in the same PowerShell window and then activate the environment again:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\venv\Scripts\Activate.ps1
```

### 3. Install dependencies

```powershell
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### 4. Train the forecasting models

Set the Python module path and run the training pipeline:

```powershell
$env:PYTHONPATH = '.'
python train_pipeline.py
```

Training must be completed once before the dashboard can show model metrics. It saves models under `models/`, processed data under `data/processed/`, figures under `results/figures/`, and metric/prediction files under `results/`. TensorFlow 2.21.0 is required for the LSTM stage.

### 5. Start the Flask application

```powershell
python app.py
```

Open `http://127.0.0.1:5000` in a browser. On first application start, SQLite tables are created automatically. Register an account, add products, record sales, and review inventory alerts.

A customer-created product with fewer than 30 sales observations returns an honest insufficient-history response; the application never reuses the global demonstration model for an unrelated customer product.

## API

- `GET /api/stores`
- `GET /api/products`
- `GET /api/model-metrics`
- `POST /api/forecast` with `store_id`, `product_id`, `horizon` (7, 14, or 30), and optional `model`
- `POST /api/inventory-recommendation` with the forecast fields plus optional `lead_time` and `service_level`

Authenticated wholesale APIs include `GET /api/me`, product CRUD at `/api/products`, sales at `/api/sales`, `/api/inventory`, `/api/alerts`, `/api/alerts/<id>/read`, `/api/dashboard-summary`, and `/api/forecasts/<product_id>`.

## Importing Customer Data

Customers can import operational data from the My Products and Sales pages using CSV or XLSX files. Product imports accept `Product Name`, `Category`, `Unit`, and `Current Stock`; sales imports accept `Date`, `Product`, `Quantity Sold`, and optional `Unit`, `Amount`, and `Buyer`. Downloadable CSV templates are available on each import page.

Imports are previewed and validated before confirmation. Product names are matched case-insensitively and existing products are not duplicated. Sales dates cannot be in the future, quantities must be positive, units must match the registered product when supplied, and sales for another or unknown user's product are rejected. Duplicate product and sales records are reported and skipped. Imported historical sales do not deduct current inventory; imported product stock does enter the existing inventory and alert calculations.

Imported rows are stored in the authenticated customer's SQLite records and remain isolated by `user_id`. The customer forecasting page reads those sales records through the existing customer-specific forecasting workflow. A customer model must still be trained with the existing minimum history requirement before forecasting; imports do not retrain production models automatically. Customer imports are separate from the read-only benchmark file `data/raw/sales_data.csv`, which is never modified.

## Testing

```powershell

```

The current suite covers dataset integrity and inventory formulas plus registration, login, protected routes, duplicate emails, wrong passwords, multi-user product isolation, oversell rejection, inventory updates, and insufficient-history forecast handling.

## Limitations and future work

The dataset contains no supplier lead-time field, so lead time remains configurable. The current univariate SARIMA/LSTM comparison uses a reference series; the dashboard supports persisted LSTM inference for that selected model and tree-model inference for other store-product pairs. Future work can add per-series LSTM/SARIMA artifact management, rolling-origin validation, richer exogenous-variable availability rules, and model monitoring.

Sales suggestions use a weighted average of up to seven recent, actual, non-future sales for the logged-in user and product. A suggestion is only a prefill helper; it never inserts a sale. The saved `entry_method` distinguishes `Manual` from `Suggested + Confirmed`. Sales cannot use future dates or exceed current stock. Stock receipts are stored as `STOCK_IN` inventory transactions.

### Customer-specific forecasting

Customer models are separate from the global benchmark models and are stored under `customer_models/user_<id>/product_<id>/`. The customer LSTM uses a 30-record lookback sequence and a chronological 60% training, 20% validation, and 20% test split. The implementation requires at least 54 actual records: `int(0.60 * 54) - 30 = 2` training sequences, with non-empty validation and test sequences. The scaler is fitted only on the training prefix. Model metadata records the user, product, record count, sequence length, dates, and evaluation metrics. New sales make the persisted model stale until retraining.

For the live Jaggery product, SQLite currently contains 36 actual records dated 2026-08-15 through 2026-09-17. Therefore it is correctly shown as `not_trained` with `required_records: 54`; no forecast is generated and no values are fabricated. Inventory remains available independently.
